# カスタムダンプ 要求整理

## 1. システム概要

カーネルクラッシュ時に、指定の構造体でカスタムデータをダンプし、
標準 kdump の vmcore から参照できる形で保存する独自ダンプ機能を実装する。

参考実装: `linux-yocto_kdump_ko`

---

## 2. vmcore 統合要件

### 2.1 要件

カスタムダンプの内容を vmcore に含めること。含める方法は実装上の最善手を選択する。

### 2.2 統合方式の検討

| 方式 | 概要 | メリット | デメリット |
|------|------|---------|-----------|
| **PT_LOAD 追加** | 固定物理領域を専用セグメントとして elfcorehdr に追加 | `/proc/vmcore` から直接読み出せる。解析ツールが標準のセグメント走査で発見可能 | elfcorehdr 生成（`crash_load_segments`）がカーネル側処理のため、純粋なモジュールのみでは実現不可 |
| **PT_NOTE 追加** | ELF NOTE セグメントにカスタムデータを埋め込む | 小サイズのメタ情報に向く | 大容量データには不向き |
| **vmcoreinfo のみ** | 物理アドレスを vmcoreinfo シンボルとして公開 | 実装が最小限 | 解析側で物理アドレスを別途解決する処理が必要 |

### 2.3 結論：PT_LOAD 追加を採用

固定物理領域に書き込んだカスタムデータを vmcore に含める方法として、
**PT_LOAD セグメントとして elfcorehdr に追加する方式**を採用する。

採用理由:

- 固定物理領域のサイズが大きく（数十 MB 想定）、PT_NOTE・vmcoreinfo には不向き
- crash kernel の `/proc/vmcore` を読むだけでカスタム領域にアクセスでき、解析ツール側の実装が単純になる
- `linux-yocto_kdump_ko` において同方式（`append_kdmp_load_header`）が実績として存在する

> **注記**: PT_LOAD 以外の方式が要件上より適切と判断される場合は再検討する。

---

## 3. 実装方式の選定

### 3.1 要素技術の整理

実装方式を選定するにあたり、必要な機能とカーネル側での対応状況を整理する。

| 必要な機能 | カーネル変更 | モジュールのみ | 備考 |
|-----------|------------|-------------|------|
| 固定物理領域の予約 | 必須 | 不可 | `memblock` は早期ブート専用。`memmap=` パラメータはカーネル側処理 |
| PT_LOAD 追加 | 必須 | 不可 | `crash_load_segments()`（`arch/x86/kernel/crash.c`）はカーネル側処理 |
| CPU例外 pt_regs 取得 | 不要 | 可能 | `register_die_notifier()` が `EXPORT_SYMBOL_GPL` 済み |
| NMI pt_regs 取得 | 不要 | 可能 | `__register_nmi_handler()` が `EXPORT_SYMBOL` 済み |
| panic 時レジスタ保存 | 不要 | 可能 | `panic_notifier_list` への登録はモジュールから可能 |

物理領域予約と PT_LOAD 追加はカーネル側への変更が必須であり、
純粋なモジュールのみでの完全実装は不可能である。

### 3.2 実装方式の比較

#### 方式 A：純粋モジュール（カーネル変更なし）

```
カーネル側: memmap= で物理領域を予約（ユーザーが設定）
モジュール側: register_die_notifier / register_nmi_handler / panic_notifier のみ
```

- PT_LOAD は追加されない → vmcore からカスタム領域への直接アクセス不可
- vmcoreinfo にシンボルを公開し、解析ツール側でアドレスを解決する運用になる
- カーネルソース変更ゼロ。モジュールのみでデプロイ可能

概算コード行数: **約 360 行**（PT_LOAD 要件未達のため採用不可）

内訳:
- データ構造定義 + 書き込みロジック（共通）: 約 260 行
- モジュール init/exit・`memremap()`・notifier 登録 glue: 約 100 行

#### 方式 B：kprobes を利用したモジュール

```
カーネル側: memmap= で物理領域を予約
モジュール側: kprobe/kretprobe を各所に設置
```

**pt_regs 取得の限界:**

- `__die_body`、`__die`、`oops_begin`、`oops_end` はすべて `NOKPROBE_SYMBOL` のため kprobe 設置不可
- `die()` 自体は NOKPROBE 対象外だが、kprobe 時点の pt_regs は die() エントリ時のレジスタ状態であり、
  元の例外時の pt_regs は引数（rsi）経由で間接的にしかアクセスできない
- `register_die_notifier(DIE_OOPS)` で同等の情報が直接取得できるため kprobes を pt_regs 取得に
  使うメリットは実質ない

**kprobes による PT_LOAD 追加（技術的な可否）:**

PT_LOAD は `kexec -p` 実行時に `crash_load_segments()` → `prepare_elf_headers()` の流れで
elfcorehdr バッファに書き込まれる。モジュール側から kprobes を使って割り込む手順は以下の通り。

```
① kretprobe on arch_crash_get_elfcorehdr_size()
   → return 値に sizeof(Elf64_Phdr) を加算
   → prepare_elf_headers() が確保するバッファに PT_LOAD 1件分の余白を作る

② kretprobe on prepare_elf_headers()
   → 関数の第1引数（ELF バッファポインタ）を取得
   → ELF ヘッダの e_phnum を読んで末尾オフセットを計算
   → カスタム物理領域の PT_LOAD エントリを末尾に書き込み
   → e_phnum を +1 更新
```

この手順は一応動作する可能性があるが、以下の問題がある:

| 問題 | 内容 |
|------|------|
| 関数シグネチャの安定性なし | `prepare_elf_headers()` は内部 API であり、引数・バッファ形式はカーネルバージョン間で変化する可能性がある |
| ① ② の原子性なし | size 加算と PT_LOAD 書き込みが別の kprobe ハンドラに分かれるため、他のコンテキストが割り込む余地がある |
| モジュールロード順序制約 | `kexec -p` の前にモジュールがロードされていなければ kprobe が有効にならず PT_LOAD は追加されない（方式 C・D も同様の制約があるが、方式 C はフラグで明示的に管理される）|
| 方式 C との比較 | 方式 C では `append_kdmp_load_header()` という専用パスが設けられており、サイズ予約（`arch_crash_get_elfcorehdr_size()`）との整合が設計レベルで保証されている。kprobes では同等の保証が得られない |

結論として、kprobes で PT_LOAD 追加は「動く可能性はあるが実用上の信頼性に欠ける」。

概算コード行数: **約 460 行**（PT_LOAD 信頼性低）

内訳:
- データ構造定義 + 書き込みロジック（共通）: 約 260 行
- モジュール init/exit・`memremap()`・notifier 登録 glue: 約 100 行
- kretprobe on `arch_crash_get_elfcorehdr_size()` + on `prepare_elf_headers()`（ELF パース・PT_LOAD 書き込み）: 約 100 行

#### 方式 C：ビルトイン＋カーネルモジュール（参考実装と同方式）

```
カーネル側（ビルトイン）:
  - 物理領域予約（setup.c の early boot 処理）
  - PT_LOAD 追加（crash.c の crash_load_segments 内）
  - 関数ポインタのエクスポート（モジュールが登録できる hook を提供）
    例: panic_dump_gprs (kernel/panic.c)
        nmi_dump_gprs  (arch/x86/kernel/nmi.c)
        ipi_dump_gprs  (arch/x86/kernel/reboot.c)
        kdmp_event_hook (arch/x86/kernel/dumpstack.c)
        kdmp_ecxt_regs (arch/x86/kernel/dumpstack.c)

モジュール側:
  - データ構造への書き込み処理
  - PCI/IO レジスタ取得
  - panic_notifier 登録
  - 上記関数ポインタへのコールバック設定
```

- カーネル側の最小限の変更（関数ポインタ追加とエクスポート）でモジュール化できる
- 参考実装（`linux-yocto_kdump_ko`）はこの方式を採用している
- PT_LOAD 追加・物理領域予約は確実に行われる
- モジュール単体の配布・更新が可能

概算コード行数: **約 430 行**（全要件充足）

内訳:
- データ構造定義 + 書き込みロジック（共通）: 約 260 行
- カーネル側 hook 層（`kdmp_res`・PT_LOAD・関数ポインタ宣言・EXPORT_SYMBOL_GPL・フック呼び出し）: 約 90 行
- モジュール側 glue（init/exit・`memremap()`・関数ポインタ登録・panic_notifier）: 約 80 行

#### 方式 D：完全ビルトイン

```
カーネル側:
  すべての機能をカーネルソースに直接実装
モジュールなし
```

- PT_LOAD 追加・物理領域予約・データ書き込みのすべてがカーネル内で完結
- 運用上の順序制約なし
- 変更のたびにカーネル再ビルドが必要

概算コード行数: **約 380 行**（全要件充足）

内訳:
- データ構造定義 + 書き込みロジック（共通）: 約 260 行
- カーネル直接実装（`setup.c` 予約・`crash.c` PT_LOAD・`dumpstack.c` / `nmi.c` / `panic.c` フック）: 約 120 行
- 関数ポインタ層・モジュール glue なし

### 3.3 比較まとめ

| 観点 | A: 純粋モジュール | B: kprobes | C: ビルトイン＋モジュール | D: 完全ビルトイン |
|------|----------------|-----------|------------------------|----------------|
| カーネル変更 | なし（memmap= のみ） | なし | 最小限（hook エクスポート）| 大（全機能）|
| PT_LOAD 対応 | 不可 | 条件付き可能（注1） | 可能 | 可能 |
| PT_LOAD の信頼性 | — | 低（内部 API 依存、注1） | 高（設計で保証） | 高 |
| 物理領域予約 | memmap= のみ | memmap= のみ | カーネル側で管理 | カーネル側で管理 |
| pt_regs 取得精度 | die_notifier 経由で十分 | kprobe 経由（間接的、注2） | 専用フック（直接） | 直接 |
| デプロイ容易性 | モジュール単体 | モジュール単体 | モジュール単体 | カーネル再ビルド |
| 実装難易度 | 低 | 高（NOKPROBE + ELF 操作）| 中 | 中 |
| **概算コード行数** | **約 360 行（要件未達）** | **約 460 行（PT_LOAD 信頼性低）** | **約 430 行** | **約 380 行** |
| 全要件充足 | ✗ | △ | ✓ | **✓** |

**注1 (B: kprobes の PT_LOAD):**  
`arch_crash_get_elfcorehdr_size()` に kretprobe でサイズを水増しし、
`prepare_elf_headers()` に kretprobe でバッファ末尾に PT_LOAD を書き込むことで技術的には追加可能。
ただし `prepare_elf_headers()` は内部 API（シグネチャ・バッファ形式がバージョン間で変化する可能性）であり、
サイズ加算と PT_LOAD 書き込みが別ハンドラに分かれるため原子性が保証されない。
実用上の信頼性は低い。

**注2 (B: kprobes の pt_regs):**  
`__die_body`・`__die`・`oops_begin`・`oops_end` はすべて `NOKPROBE_SYMBOL` のため直接 attach 不可。
`die()` 自体は kprobeable だが、元の例外時 pt_regs は引数（rsi）経由での間接取得になる。
`register_die_notifier(DIE_OOPS)` で同等情報を直接取得できるため kprobes の優位性はない。

### 3.4 結論：方式 D（完全ビルトイン）を採用

**採用方針: 全要件を充足する方式の中でコード行数が最小のものを選択する。**

- 全要件を充足する方式は C（約 430 行）と D（約 380 行）
- D は C より約 50 行少ない。差分の主因は方式 C に必要な関数ポインタ層（カーネル側 ~90 行）とモジュール glue（~80 行）の合計 ~170 行に対し、方式 D のカーネル直接実装が ~120 行で済むこと
- モジュール分離（方式 C）は更新時の柔軟性があるが、hook エクスポート・関数ポインタ・モジュール登録という3層の glue コードが余分に発生する
- A は PT_LOAD 要件未達、B は PT_LOAD の実用信頼性が低いため除外
- 方式 D を採用し、完全ビルトインとして実装する

## 4. 固定物理領域の確保方法

### 4.1 参考実装（kdump_ko）の現状

`linux-yocto_kdump_ko` の `reserve_panic_dump()` は `memblock_phys_alloc_range()` による
**動的確保**であり、固定物理アドレスではない。ブートごとにアドレスが変わる可能性がある。

```c
// arch/x86/kernel/setup.c（参考実装）
kdmp_base = memblock_phys_alloc_range(kdmp_size, PMD_SIZE, 0, alloc_end);
// → 空き領域から動的に割り当て。アドレスは不定
```

### 4.2 固定物理アドレスが必要な理由

- 解析ツールをアドレス固定で設計できる
- vmcoreinfo の解析が不要になる
- ファームウェア（BIOS/UEFI）側で同じ領域を予約している場合、衝突を防げる

### 4.3 固定物理領域の指定方法

#### 方法 1：`memmap=` カーネルパラメータ（推奨）

```
カーネルパラメータ:
  memmap=64M$0x10000000

  書式: memmap=<サイズ>$<物理アドレス>
  例:   memmap=64M$0x10000000
        → 物理 0x10000000 から 64MB を予約
        → E820_TYPE_RESERVED としてマーク（カーネルが RAM として使用しない）
```

モジュール側でのアクセス:
```c
// モジュール init 時
void *vaddr = memremap(0x10000000, 64 * 1024 * 1024, MEMREMAP_WB);
// または
void __iomem *vaddr = ioremap(0x10000000, 64 * 1024 * 1024);
```

crash.c での PT_LOAD 追加:
```c
// crash.c 側でハードコードまたはカーネルパラメータ解析後の値を参照
kdmp_res.start = 0x10000000;
kdmp_res.end   = 0x10000000 + 64*1024*1024 - 1;
```

利点:
- カーネルソースの変更が不要
- アドレスがブートをまたいで固定される
- GRUB の設定で管理できる

欠点:
- ハードウェア構成によっては指定アドレスに RAM が存在しない場合がある
- `memmap=` は他の用途（EFI 等）と競合しないよう注意が必要

#### 方法 2：`early_param` によるカーネルパラメータ追加

`setup.c` にカスタムパラメータを追加し、指定アドレスを `memblock_reserve()` で予約する。

```c
// arch/x86/kernel/setup.c に追加
static phys_addr_t custom_dump_phys_base;
static resource_size_t custom_dump_phys_size;

static int __init parse_custom_dump(char *arg)
{
    // "size@addr" 形式を解析
    // 例: custom_dump=64M@0x10000000
    phys_addr_t base;
    resource_size_t size;
    // ... 解析処理 ...
    memblock_reserve(base, size);
    custom_dump_phys_base = base;
    custom_dump_phys_size = size;
    return 0;
}
early_param("custom_dump", parse_custom_dump);
```

利点:
- 専用パラメータで意図が明確
- カーネル側で管理するため `kdmp_res` への統合が容易

欠点:
- カーネルソースへの変更が必要

#### 方法の選択

| 条件 | 選択 |
|------|------|
| カーネルソース変更を避けたい | `memmap=` |
| 専用パラメータで管理したい、またはカーネル変更が許容できる | `early_param` 追加 |

## 5. カスタムダンプ仕様

### 5.1 CPU例外・NMI 汎用レジスタ情報

#### 5.1.1 取得タイミングとフック先

方式 D（完全ビルトイン）での実装を前提とする。

| 例外種別 | フック箇所 | 方法 |
|----------|-----------|------|
| CPU例外全般（#DE/#PF/#GP 等） | `__die_body()`（`dumpstack.c`）| カーネル内に直接実装。`pt_regs *` を受け取りバッファへ書き込む |
| NMI | `arch/x86/kernel/nmi.c` の NMI ハンドラ | カーネル内に直接実装。NMI 時の `pt_regs *` をバッファへ書き込む |
| panic 全経路 | `panic()`（`kernel/panic.c`）| カーネル内に直接実装（panic フック）。拡張レジスタ・PCI/IO もここで収集 |

#### 5.1.2 保存データ構造（1エントリ）

```c
struct custom_excp_entry {
    /* CPUレジスタ */
    struct pt_regs    regs;           // 汎用レジスタ全て (RIP/RSP/RFLAGS含む)
    unsigned long     cr2;            // #PF 用フォルトアドレス（die 時点で取得）

    /* 例外情報 */
    unsigned int      trap_nr;        // 例外ベクタ番号 (current->thread.trap_nr)
    unsigned long     error_code;     // CPU が積んだエラーコード

    /* プロセス情報 */
    pid_t             pid;            // current->pid
    pid_t             tgid;           // current->tgid
    char              comm[16];       // current->comm

    /* コンテキスト */
    int               cpu;            // raw_smp_processor_id()
    int               preempt_count;  // 割り込み/softirq/NMI ネスト深さ
    uint64_t          timestamp;      // ktime_get() 等

    uint8_t           rsv[...];       // 将来拡張用パディング
};
```

#### 5.1.3 ヒストリーバッファ構造

```c
#define CUSTOM_EXCP_HISTORY_MAX  5

struct custom_excp_ring {
    uint32_t                  count;    // 累計発生回数
    uint32_t                  head;     // 最新エントリのインデックス (0–4)
    struct custom_excp_entry  entries[CUSTOM_EXCP_HISTORY_MAX];
};
```

- **最初の取得値**: `entries[0]` に格納
- **以降**: `count % 5` の位置に上書き（リングバッファ）
- **最大保存数**: 5件（古いものから上書き）

#### 5.1.4 CPU コア別バッファ

CPU コアごとに独立した `custom_excp_ring` を持つ。

### 5.2 panic notifier でのレジスタ情報

panic 発生時（`#MC` の `mce_panic()`・`nmi_panic()` → `panic()` を含む全経路）に
`panic_notifier_list` 経由で以下を取得・保存する。

#### 5.2.1 CPU 拡張レジスタ

| カテゴリ | 内容 | 取得方法 |
|---------|------|---------|
| 制御レジスタ | CR0, CR2, CR3, CR4 | `read_crN()` |
| デバッグレジスタ | DR0–DR7 | `get_debugreg()` |
| セグメント記述子 | GDT, IDT, LDT, TR | `store_gdt()` 等 |
| MSR | EFER, APIC_BASE, IA32_MISC 等 | `rdmsrl()` |
| ローカル APIC | 全レジスタ | MMIO 読み出し |
| FPU/SIMD | x87/SSE/AVX 状態 | `fpu__save()` 等 |
| CPUID | 機能フラグ | `cpuid()` |

#### 5.2.2 システムレジスタ情報

| カテゴリ | 内容 |
|---------|------|
| PCI コンフィグ空間 | 指定デバイスのレジスタ一覧 |
| IO ポート | 指定アドレスの IO レジスタ |
| メモリマップド IO | 指定範囲の MMIO レジスタ |

### 5.3 全体のダンプ領域レイアウト

```
固定物理領域 (例: 64MB at 0x10000000)
┌──────────────────────────────────────────┐
│ custom_dump_header                       │  magic, format, timestamp, flags
├──────────────────────────────────────────┤
│ custom_excp_ring [NR_CPUS]               │  CPU例外・NMI ヒストリー (5.1)
│   └─ entries[5] × CPU コア数            │
├──────────────────────────────────────────┤
│ custom_cpu_regs [NR_CPUS]                │  panic 時 CPU 拡張レジスタ (5.2.1)
│   CR/DR/MSR/APIC/FPU 等                 │
├──────────────────────────────────────────┤
│ custom_pci_regs                          │  PCI/IO/MMIO レジスタ (5.2.2)
├──────────────────────────────────────────┤
│ printk ring buffer snapshot              │  クラッシュ直前ログ
└──────────────────────────────────────────┘
```

## 6. 実装ポイントサマリー

| 機能 | 実装側 | 実装方針 |
|------|--------|---------|
| 固定物理領域予約 | カーネル（`setup.c`）| `memblock_reserve()` で早期ブート時に確保 |
| vmcore への統合 | カーネル（`crash.c`）| `arch_crash_get_elfcorehdr_size()` 拡張 + `append_kdmp_load_header()` 実装 |
| CPU例外 pt_regs 取得 | カーネル（`dumpstack.c`）| `__die_body()` 内に直接実装し、固定領域へ書き込み |
| NMI pt_regs 取得 | カーネル（`nmi.c`）| NMI ハンドラ内に直接実装し、固定領域へ書き込み |
| ヒストリー管理 | カーネル（共通）| 固定領域内のリングバッファ（最大5件）、`count % 5` で上書き |
| panic 時レジスタ保存 | カーネル（`panic.c`）| `panic()` 内に直接実装、CR/DR/MSR/APIC/FPU/PCI/IO を収集して書き込み |
| vmcoreinfo 公開 | カーネル | `VMCOREINFO_SYMBOL()` で物理アドレス・サイズを crash kernel から参照可能に |
