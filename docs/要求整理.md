# 独自ダンプ方式の要求整理

## 前提

- 比較対象は以下の3方式とする。
- ビルトイン: 予約領域管理、CPU例外/NMI/panicフック、PT_LOAD追加、`vmcoreinfo` への構造体公開までをすべて `vmlinux` 側で実装する方式。
- ビルトイン+モジュール: 現行 `linux-yocto_kdump_ko` を基準にしたハイブリッド方式。`arch/x86/kernel/setup.c` の予約領域確保、`arch/x86/kernel/crash.c` の PT_LOAD 追加、`arch/x86/kernel/vmcore_info_64.c` の `vmcoreinfo` 連携はビルトイン側、実データ収集は `arch/x86/kdmp/*.c` モジュール側で持つ方式。
- 完全モジュール: カーネル本体への専用フック追加を極力行わず、予約領域はブートパラメータで先に確保し、収集は `panic_notifier`、`register_die_notifier`、`kprobes`、`kretprobes`、`register_vmcore_cb()` など既存 API だけで成立させる方式。
- 現行実装の確認結果として、`linux-yocto_kdump_ko` では以下がすでに成立している。
	- 予約領域は `arch/x86/kernel/setup.c` の `reserve_panic_dump()` で確保される。
	- vmcore の PT_LOAD 追加は `arch/x86/kernel/crash.c` の `append_kdmp_load_header()` で実施される。
	- panic notifier と各種レジスタ収集本体は `arch/x86/kdmp/kdmp_setup.c`、`arch/x86/kdmp/kdmp_dump.c` にある。
	- ただし `kdmp_kdmp_primary` と `kdmp_kdmp_slot[]` の `VMCOREINFO_SYMBOL()` は `IS_BUILTIN(CONFIG_CUSTOM_CRASHCUMP)` 条件下のみで、モジュール構成のままでは crash からの型付きシンボル参照性が弱い。

## 要求ごとの実装イメージ

| 観点 | ビルトイン | ビルトイン+モジュール | 完全モジュール |
| --- | --- | --- | --- |
| ① 独自ダンプ領域を `memmap` で指定 | `memmap=` で 2 領域を予約し、`setup_arch()` 早期で `memblock_reserve()` 相当の扱いにする。`cpu_dump_res`、`device_dump_res` を `struct resource` として `vmlinux` 側に持つ。 | 現行の `kdmp_res` と同じ考え方で予約領域管理だけをビルトインに残し、モジュールは `memremap()` で使用する。2 領域に分割するなら `kdmp_cpu_res`、`kdmp_dev_res` のようにビルトインで資源名を分ける。 | 領域確保そのものはモジュールではできないため、`memmap=` で予約済み領域を前提にモジュールが `request_mem_region()` と `memremap()` を行う。予約漏れ時の自己回復はできない。 |
| ② vmcore の PT_LOAD に 2 領域追加 | `arch/x86/kernel/crash.c` で ELF header 生成時に CPU 領域とデバイス領域の 2 本を PT_LOAD 追加する。panic 時点で必ずヘッダに反映できる。 | PT_LOAD の追加処理はビルトインに置き、モジュールは `kdmp_active` 相当の活性制御と、各領域に書く実データだけを担当する。現行実装の延長で最も自然。 | 収集自体は `panic_notifier` と `kprobes`/`kretprobes` で行い、PT_LOAD 追加は既存の `register_vmcore_cb()` または capture kernel 側の `get_device_ram()` 連携に寄せる案になる。panic kernel と capture kernel の責務分離が必要で最も複雑。 |
| ③ crash 解析しやすいよう構造体をシンボル表示 | `VMCOREINFO_SYMBOL()` と `VMCOREINFO_STRUCT_SIZE/OFFSET()` を `vmlinux` 側で定義できる。`custom_cpu_dump_area`、`custom_device_dump_area` のようなグローバル名をそのまま crash で引ける。 | 現行のままだとモジュール変数は `VMCOREINFO_SYMBOL()` に乗らないため弱い。満たすには「構造体アンカー変数だけをビルトインに持ち、モジュールはその中身を書くだけ」に再設計する必要がある。 | モジュールシンボル自体は crash で読める場合もあるが、`vmlinux` 標準の `vmcoreinfo` に統合されず、解析時に対象モジュールのデバッグ情報とロード状態への依存が増える。要求適合性は最も低い。 |
| ④ 汎用 CPU レジスタを panic/致命例外/NMI でフック | `do_trap`、`__die_body()`、`panic()`、`nmi_panic()` 近傍に直接フックを置ける。panic は既存 `crash_notes` の CPU 情報を採用し、独自領域には補助情報だけ残す制御も容易。 | 現行方式と同様に、例外/NMI の入り口にビルトインの軽量 hook point を置き、保存本体はモジュールが受ける。panic は `panic_notifier`、NMI/例外は既存 hook または exported callback で拾う構成が現実的。 | 例外経路と NMI 経路を `kprobes`/`kretprobes` と `register_die_notifier()` で拾う。要求の「モジュール方式では kprobes/kretprobes を使用」は満たせるが、命令位置依存、最適化影響、再入制御が難しい。panic の CPU 情報を既存 vmcore 側に寄せる分岐も煩雑。 |
| ⑤ 指定構造体へ最大 5 個まで保存 | `struct custom_cpu_record { struct pt_regs regs; u32 cpuid; u32 cpu; u32 vector; u32 app_id; u64 ts_nsec; ... }` と `struct custom_cpu_ring { u32 count; struct custom_cpu_record rec[5]; }` を `vmlinux` に定義し、最初の値を正とし以降 5 件まで append する。 | 構造体定義自体はビルトインに置き、更新ロジックだけをモジュールに置くと crash 解析性と変更容易性の両立ができる。現行 `kdmp_data_t` を 2 領域化して拡張する形がやりやすい。 | 構造体もモジュール定義に寄りがちで、③ と同じく解析性が落ちる。ロックレスで 5 件まで追記するリング実装自体は可能だが、NMI/例外/ panic 競合時の整合性検証が重い。 |
| ⑥ デバイスダンプを `panic_notifier` で実施 | panic 直前に `panic_notifier` から `ioremap` 済みベースアドレスを使って約 50 件の `(offset,size)` を採取する。PT_LOAD へ載せるデバイス領域は固定長で管理できる。 | 現行 `kdmp_panicdump_exec()` の役割をそのまま拡張しやすい。事前 `ioremap` とレジスタ表解決はモジュールで持ち、ビルトインは領域と PT_LOAD だけ管理する構成が最も分離しやすい。 | panic notifier 自体は使えるが、ベースアドレス解決対象のカーネル内部 API や PCI/MMIO の参照点をすべてモジュールだけで追う必要がある。将来のカーネル差分に弱い。 |
| ⑦ 特定ユーザーアプリのみ fatal で panic、panic 時 watchdog 停止 | `get_signal()`、`do_exit()`、例外配送経路などに条件判定を直接入れられる。watchdog 停止も panic パスに同期して確実に実行しやすい。 | ポリシー判定用の軽量 hook をビルトインに追加し、対象アプリ判定テーブルや watchdog 停止処理本体はモジュールに持たせると保守しやすい。 | `get_signal`、`do_group_exit`、`force_sig_fault`、`watchdog` 関連関数へ `kprobe`/`kretprobe` を貼る案になる。実現は可能だが誤判定とバージョン追従リスクが高い。 |

## 各方式の評価

### 1. ビルトイン

実装イメージ:

- 2 つの予約領域を `vmlinux` 側の `struct resource` と固定シンボルで持つ。
- 例外、NMI、panic、fatal signal 判定、watchdog 停止までをカーネル本体に直実装する。
- PT_LOAD 2 本追加、`vmcoreinfo` の型公開、crash 解析用シンボル公開をすべて `vmlinux` 側で完結させる。

メリット:

- もっとも確実に ① から ⑦ を満たせる。
- panic/NMI/例外の最悪タイミングでもフック取りこぼしが最少。
- crash 解析性が最も高く、構造体名と変数名をそのまま運用できる。

デメリット:

- カーネル本体の差分が大きくなり、保守範囲が広い。
- upstream 差分追従、再ベース、コードレビュー負荷が最も重い。

評価:

- 実装難易度: 高
- テスト検証量: 高
- 実装量: 高

### 2. ビルトイン+モジュール

実装イメージ:

- 現行 `linux-yocto_kdump_ko` をベースにする。
- 予約領域管理、PT_LOAD 追加、`vmcoreinfo` の固定アンカーはビルトインに残す。
- CPU レジスタ収集、デバイスダンプ収集、対象アプリ判定、watchdog 停止処理の詳細はモジュールに置く。
- requirement ③ を満たすため、少なくとも crash で直接見たい構造体の実体ポインタだけはビルトイン側へ移す。

メリット:

- 現行資産を最も再利用しやすい。
- ② の PT_LOAD 追加はすでに現行実装の延長で実現できる。
- 本体改造を最小限に抑えつつ、panic 前後の確実性をかなり確保できる。

デメリット:

- ビルトインとモジュールの責務境界設計が必要。
- ③ は現行のままでは未達で、アンカー変数のビルトイン化が追加で必要。
- モジュール未ロード時のフォールバック動作を決める必要がある。

評価:

- 実装難易度: 中
- テスト検証量: 中から高
- 実装量: 中

### 3. 完全モジュール

実装イメージ:

- 予約領域は `memmap=` で確保済みとし、モジュールはそれを見つけて `memremap()` するだけにする。
- panic は `panic_notifier`、例外/NMI/fatal signal は `register_die_notifier()` と `kprobes`/`kretprobes` で取得する。
- PT_LOAD 追加は `register_vmcore_cb()` や capture kernel 側 callback を使って後付けする。
- デバイスダンプ、watchdog 停止、対象アプリ判定もモジュールで完結させる。

メリット:

- カーネル本体差分を最小化できる。
- 機能の追加削除をモジュール差し替えで行いやすい。

デメリット:

- ① は満たせても「予約漏れ時に救えない」。
- ② と ④ と ⑦ の成立性が kprobe 位置と既存 API に強く依存し、最も壊れやすい。
- ③ の crash 解析性が弱く、運用時に追加シンボルロードの手順が増える。
- panic/NMI の最悪タイミングでモジュールコードに依存するため、信頼性評価が重い。

評価:

- 実装難易度: 高
- テスト検証量: 非常に高い
- 実装量: 中から高

## 結論

- 第一候補は ビルトイン+モジュール。
- 理由は、現行 `linux-yocto_kdump_ko` の資産を活かしつつ、① 予約領域、② PT_LOAD 追加、④ panic/NMI/例外のフック確実性をビルトイン側で担保できるためである。
- ただし requirement ③ の「crash で構造体を変数名付きで追えること」は、現行モジュール構成のままでは弱い。`custom_cpu_dump_area`、`custom_device_dump_area`、あるいはそれらを指すポインタ配列だけでも `vmlinux` 側に固定シンボルとして置く設計変更が必要である。
- ビルトインは最も堅いが、本体改造量と保守負荷が重い。製品として長期固定し、解析性を最優先する場合に向く。
- 完全モジュールは一見差分が少ないが、② ④ ⑦ の実現が `kprobes`/`kretprobes` 依存となり、テスト量と障害時の不確実性が大きい。今回要求の性質では優先度は最も低い。

## 推奨実装方針

- 予約領域は `memmap=` で CPU 領域とデバイス領域の 2 本を固定確保する。
- PT_LOAD 追加はビルトイン側で 2 本を確実に追加し、モジュールは内容充填のみに責務を限定する。
- crash 向けの構造体定義、配列、アンカー変数名はビルトイン側に置く。
- panic の CPU 情報は既存 vmcore の `crash_notes` を正として採用し、独自領域には補助情報と履歴最大 5 件を保存する。
- デバイスダンプは panic notifier で実施し、現行同様に事前 `ioremap` と `(offset,size)` テーブル方式を維持する。
- 特定アプリのみ fatal で panic させる判定と watchdog 停止は、少なくとも判定フックだけはビルトイン化し、ポリシー詳細をモジュールに逃がす構成を推奨する。

## 検討結果

- 第 1 候補は「ビルトイン+モジュール」とする。
- 理由は以下のとおり。
	- 現行 `linux-yocto_kdump_ko` の資産を最も活用できる
	- ① 予約領域確保と ② PT_LOAD 追加はビルトインで安定化できる
	- ⑥ デバイスダンプ対象や ⑦ アプリ致命化ポリシーはモジュール化した方が運用しやすい
	- 完全モジュール方式で必須になる `kprobe/kretprobe` 依存を最小化できる

- ただし、第 1 候補を要求 ③ まで満たす形にするには、現行実装から以下の補強が必要である。
	- CPU 領域とデバイス領域を分離し、PT_LOAD を 2 本追加する
	- `cpu_custom_dump_primary`、`dev_custom_dump_primary`、`cpu_custom_dump_slot[]` など解析用アンカー変数を vmlinux 側へ移す
	- `VMCOREINFO_SYMBOL()` / `VMCOREINFO_OFFSET()` を vmlinux 側で定義し、module build でも crash 解析しやすくする
	- panic 時 CPU レジスタは標準 vmcore を正本とし、独自領域は例外/NMI と補足メタ情報中心に整理する

- 第 2 候補は「ビルトイン」である。
- 長期的な保守対象が限定され、カーネル差分を許容できるなら最も堅牢である。

- 「完全モジュール」は非推奨とする。
- 特に ② PT_LOAD 追加、③ `crash` 解析性、④ 致命例外/NMI の取りこぼし防止、⑦ 特定アプリのみ panic 化の 4 点でリスクが高い。

## 推奨実装イメージ

- vmlinux 側
	- `memmap=` で確保した 2 領域を `cpu_dump_res` / `dev_dump_res` として early init で確定
	- crash ELF header 生成時に PT_LOAD を 2 本追加
	- `VMCOREINFO_SYMBOL()` と解析用アンカー変数を定義
	- 例外/NMI/panic で使う最小 hook だけを追加

- モジュール側
	- 2 領域を `memremap()` し、CPU 情報保存とデバイス保存を分離
	- `panic_notifier` でデバイスダンプを実施
	- 事前 `ioremap`、ベースアドレス解決、約 50 件の収集テーブル管理を担当
	- 特定ユーザーアプリの致命化ポリシーと watchdog 停止処理を担当

- 保存データ方針
	- panic CPU の一般レジスタ正本は既存 vmcore の `NT_PRSTATUS`
	- 独自 CPU 領域には「例外/NMI 時点の `pt_regs` + CPUID + CPU番号 + 例外番号 + アプリ番号 + 発生時刻」を最大 5 件保存
	- デバイス領域には PCI/PCIe/IO の固定レイアウトを保存
