## x86例外の3分類（Fault / Trap / Abort）

x86のCPU例外はハードウェアレベルで3種類に分類される。「fault」はページフォルト専用の言葉ではなく、ほとんどの同期例外がFault型である。

| 分類 | 保存されるEIP | 特徴 | 主な例外 |
|------|-------------|------|---------|
| **Fault** | 例外を発生させた命令を指す | 原因を取り除けば命令を再実行できる | #DE / #GP / #PF / #UD 等（大多数） |
| **Trap** | 次の命令を指す | 発生した命令の完了後に通知される | #BP / #OF / #DB（一部） |
| **Abort** | 信頼できない | 回復不能な重大エラー | #DF / #MC |

`handle_page_fault()` の "fault" は #PF（ベクタ14）専用。`force_sig_fault()` の "fault" はFault型例外から来たシグナルを送る関数という意味。

## 経路A/B/Cの違い

| | 理由 | kdmp_capture_event |
|-|------|--------------------|
| 経路A（`do_error_trap`） | シンプルな例外。共通処理で十分 | KDMP_EVENT_EXCEPTION |
| 経路B（専用ハンドラ） | 例外ごとに特有の前処理・判断が必要 | なし |
| 経路C（`handle_page_fault`） | MMU経由で正常・エラーが混在する別カテゴリ | KDMP_EVENT_PAGE_FAULT |

経路Bが共通化できない理由:
- **#GP**: enqcmd/UMIP/IOPL/VDSOの修正可能ケースを先に試す
- **#AC**: split lock検出と処理が必要
- **#MF/#XF**: FPU状態を読んでsi_codeを動的に決定する
- **#DB**: ptrace・デバッガとのやり取りが必要

## 経路A: do_error_trap → do_trap → force_sig_fault → プロセス終了

対象例外: #DE / #OF / #UD / Old_MF / #TS / #NP / #SS

```
CPU例外
    ↓
DEFINE_IDTENTRY(exc_*)
    ↓
do_error_trap(regs, error_code, str, trapnr, signr, sicode, addr)
    │  kdmp_capture_event(regs, KDMP_EVENT_EXCEPTION, trapnr, error_code)
    │      → ライブリングバッファ (kdmp_live.c) に記録
    │  notify_die(DIE_TRAP, ...) → die notifier chain (通常 NOTIFY_STOP でない)
    ↓
do_trap(trapnr, signr, str, regs, ...)
    ↓
do_trap_no_signal(tsk, trapnr, str, regs, error_code)
    │  user_mode(regs) == true → -1 を返す (die() は呼ばれない)
    ↓
force_sig_fault(signr, sicode, addr)   または   force_sig(signr)
    ↓
プロセス終了 (システム継続)
```

**各例外とシグナル詳細**

| 例外 | ベクタ | シグナル | si_code |
|------|--------|----------|---------|
| #DE Divide Error | 0 | SIGFPE | FPE_INTDIV |
| #OF Overflow | 4 | SIGSEGV | 0 |
| #UD Invalid Opcode | 6 | SIGILL | ILL_ILLOPN |
| Old #MF Coproc Seg | 9 | SIGFPE | 0 |
| #TS Invalid TSS | 10 | SIGSEGV | 0 |
| #NP Seg Not Present | 11 | SIGBUS | 0 |
| #SS Stack Fault | 12 | SIGBUS | 0 |

## 経路B: 専用ハンドラ → force_sig_fault → プロセス終了

`do_error_trap` を経由しないため `kdmp_capture_event` は呼ばれない。

### B-1: #GP General Protection (ベクタ 13)

```
exc_general_protection(regs, error_code)
    │
    ├─ enqcmd fixup → return (ENQCMD補正)
    ├─ UMIP fixup → goto exit
    ├─ fixup_iopl_exception / fixup_vdso_exception → goto exit
    └─ user_mode == true
           ↓
       gp_user_force_sig_segv(regs, X86_TRAP_GP, error_code, desc)
           ↓
       force_sig(SIGSEGV)
           ↓
       プロセス終了
```

### B-2: #BR Bound Range Exceeded (ベクタ 5)

```
exc_bounds(regs)
    │  notify_die(DIE_TRAP) → 通常継続
    └─ user_mode == true
           ↓
       do_trap(X86_TRAP_BR, SIGSEGV, "bounds", ...)
           ↓
       force_sig(SIGSEGV)
           ↓
       プロセス終了
```

### B-3: #AC Alignment Check (ベクタ 17)

```
exc_alignment_check(regs, error_code)
    │  notify_die(DIE_TRAP)
    └─ user_mode == true
       │  handle_user_split_lock → 処理できた場合は return (プロセス継続)
       └─ do_trap(X86_TRAP_AC, SIGBUS, "alignment check", ..., BUS_ADRALN)
              ↓
          force_sig_fault(SIGBUS, BUS_ADRALN, NULL)
              ↓
          プロセス終了
```

### B-4: #MF x87 FPU Error (ベクタ 16) / #XF SIMD FP Exception (ベクタ 19)

```
exc_coprocessor_error(regs)          exc_simd_coprocessor_error(regs)
    ↓                                    ↓
math_error(regs, X86_TRAP_MF)        math_error(regs, X86_TRAP_XF)
    │
    ├─ user_mode == false → die() (カーネルoops経路)
    └─ user_mode == true
           │  fpu_sync_fpstate()
           │  si_code = fpu__exception_code()
           │  si_code == 0 → return (spurious, プロセス継続)
           └─ force_sig_fault(SIGFPE, si_code, ip)
                  ↓
              プロセス終了

si_code 例: FPE_FLTDIV / FPE_FLTOVF / FPE_FLTUND / FPE_FLTRES / FPE_FLTINV / FPE_FLTSUB
```

### B-5: #NM Device Not Available (ベクタ 7) — XFD拡張機能不許可

```
exc_device_not_available(regs)
    └─ handle_xfd_event(regs) → XFD_ERR が設定されている場合
           │
           ├─ xfd_enable_feature() → -EPERM
           │      force_sig_fault(SIGILL, ILL_ILLOPC, ip)
           │          → プロセス終了
           └─ xfd_enable_feature() → -EFAULT
                  force_sig(SIGSEGV)
                      → プロセス終了
```

### B-6: #DB Debug (ベクタ 1, ユーザーモード)

```
exc_debug_user(regs, dr6)
    │  notify_debug(regs, &dr6) → デバッガが処理した場合は skip
    └─ (dr6 & DR_STEP/DR_TRAP_BITS) または icebp
           ↓
       send_sigtrap(regs, 0, si_code)
           ↓
       デバッガなしなら SIGTRAP でプロセス終了
```

### B-7: #BP Breakpoint (ベクタ 3, ユーザーモード)

```
exc_int3(regs)
    └─ user_mode == true
           ↓
       do_trap(X86_TRAP_BP, SIGTRAP, "int3", ...)
           ↓
       force_sig(SIGTRAP)
           ↓
       デバッガなしなら SIGTRAP でプロセス終了
```

### B-8: #VE Virtualization Exception (ベクタ 20, TDXゲスト)

```
exc_virtualization_exception(regs)
    └─ ve_raise_fault(regs, 0, ve.gla)
           └─ user_mode == true
                  ↓
              gp_user_force_sig_segv(regs, X86_TRAP_VE, ...)
                  ↓
              force_sig(SIGSEGV)
                  ↓
              プロセス終了
```

## 経路C: #PF Page Fault (ベクタ 14) → do_user_addr_fault → bad_area → プロセス終了

```
handle_page_fault(regs, error_code, address)
    │  kdmp_capture_event(regs, KDMP_EVENT_PAGE_FAULT, error_code, address)
    │      → ライブリングバッファに記録
    └─ fault_in_kernel_space(address) == false
           ↓
       do_user_addr_fault(regs, error_code, address)
```

## CPU例外発生からのコールツリー（ユーザー・カーネルプロセス含む）

### 共通入口

```
【CPU例外発生】
    │  ハードウェアが IDT を参照、カーネルスタックに pt_regs を保存
    ▼
asm_exc_*(アセンブリスタブ)              arch/x86/entry/entry_64.S
    ▼
exc_*(regs)  [noinstr ラッパー]          DEFINE_IDTENTRY マクロ展開
    ├─ irqentry_enter(regs)              kernel/entry/common.c:78
    │    ├─ user_mode  → irqentry_enter_from_user_mode()
    │    └─ kernel_mode → RCU・lockdep 管理
    ├─ instrumentation_begin()
    ├─ __exc_*(regs)  ─────────────────── ★ 例外ハンドラ本体（下記に分岐）
    ├─ instrumentation_end()
    └─ irqentry_exit(regs, state)        kernel/entry/common.c:185
         ├─ user_mode  → irqentry_exit_to_user_mode() ──→ 【シグナル配送】
         └─ kernel_mode → RCU・lockdep 復元
```

### カーネルoops経路（kernel_mode == true）

```
do_trap_no_signal() で !user_mode → die(str, regs, error_code)
    └─ oops_begin()
    └─ __die_body(str, regs, error_code)
         ├─ [CONFIG_CUSTOM_CRASHCUMP]
         │    kdmp_ecxt_regs[cpu] = regs    ← 例外時 pt_regs ポインタを保存
         ├─ show_regs(regs)
         └─ notify_die(DIE_OOPS, ...)
    └─ oops_end(flags, regs, sig)
         │
         ├─ kexec_should_crash(current) == 1
         │    └─ [CONFIG_CUSTOM_CRASHCUMP 無効時のみ] crash_kexec(regs) → kdump
         │
         ├─ in_interrupt() == true
         │    └─ panic("Fatal exception in interrupt") ──→ 【panic経路】
         │
         ├─ panic_on_oops == true
         │    └─ panic("Fatal exception") ──→ 【panic経路】
         │
         └─ 通常プロセス（PID≥2）
              └─ rewind_stack_and_make_dead(signr) → プロセス終了（システム継続）
```

### panic経路

```
panic(fmt) → vpanic(fmt, args)           kernel/panic.c:435
    │
    ├─ [CONFIG_CUSTOM_CRASHCUMP]
    │    panic_dump_gprs()               ← カスタムダンプ GPR 保存
    │         └─ kdmp_dump_gprs(KDMP_PANIC) / kdmp_dump_x86(KDMP_PANIC)
    │
    ├─ [crash_kexec_post_notifiers == false]
    │    __crash_kexec(NULL) ──→ kdump
    │
    ├─ panic_other_cpus_shutdown()
    │    └─ crash_smp_send_stop() → 他CPU に NMI 送信
    │         └─ crash_nmi_callback → ipi_dump_gprs() → status[IPI] へ保存
    │
    ├─ atomic_notifier_call_chain(&panic_notifier_list)
    │    └─ kdmp_panicdump_exec()        ← カスタムダンプ本体
    │
    └─ [crash_kexec_post_notifiers == true]
         __crash_kexec(NULL) ──→ kdump kernel へ
```

### 全体の分岐まとめ

```
CPU例外
    │
    ├─ user_mode == true
    │    ├─ 経路A/B/C → force_sig → シグナルキューへ追加
    │    └─ irqentry_exit_to_user_mode → arch_do_signal_or_restart
    │         └─ get_signal()
    │              ├─ 通常プロセス（PID≥2）→ handle_signal → ハンドラ or プロセス終了
    │              └─ PID 1（init）
    │                   ├─ SIG_DFL fatal → is_global_init → 無視（命令再実行）
    │                   └─ do_exit() に至った場合 → panic("Attempted to kill init!")
    │
    └─ kernel_mode == true
         ├─ fixup_exception で修正可能 → 処理続行
         └─ die() → oops_end()
              ├─ kexec_should_crash=1（CUSTOM_CRASHCUMP無効時） → 直接 kdump
              ├─ in_interrupt / panic_on_oops → panic → kdump
              └─ 通常プロセス（PID≥2） → rewind_stack_and_make_dead → プロセス終了
```

## シグナル生成と配送の2フェーズ

シグナルは「生成（キュー追加）」と「配送（ユーザー空間への受け渡し）」が分かれている。カーネル内でシグナルハンドラを直接呼ぶことはできないため、ユーザー空間復帰直前に配送を行う。

### フェーズ1: シグナル生成（例外ハンドラ内）

```
force_sig_fault(SIGSEGV, ...)
    └─ force_sig_info_to_task(&info, current, HANDLER_CURRENT)
         └─ send_signal_locked(SIGSEGV, &info, t, PIDTYPE_PID)
              ├─ __sigqueue_alloc()         ← sigqueue 構造体を確保
              ├─ list_add_tail(q, &pending) ← pending リストに追加
              └─ signal_wake_up(t, ...)     ← TIF_SIGPENDING フラグを立てる
```

この時点ではシグナルはキューに入っただけ。プロセスはまだ動いておらず、ハンドラも呼ばれていない。

### フェーズ2: シグナル配送（ユーザー空間復帰直前）

```
irqentry_exit_to_user_mode(regs)
    └─ exit_to_user_mode_loop(regs, ti_work)
         └─ TIF_SIGPENDING が立っている
              └─ arch_do_signal_or_restart(regs)   arch/x86/kernel/signal.c:333
                   └─ get_signal(&ksig)             ← キューからデキュー
                        └─ handle_signal(&ksig, regs)
                             └─ setup_rt_frame()    ← ユーザースタックにフレーム構築
                                  ├─ uc_mcontext に元の regs を保存
                                  ├─ frame->pretcode = sa_restorer
                                  └─ regs->ip = ksig->ka.sa.sa_handler ← ★ IPを書き換え
                                     regs->sp = frame
【IRET】→ ユーザー空間のシグナルハンドラへ
```

### シグナルハンドラ実行後の復帰

```
シグナルハンドラ return
    └─ pretcode（= sa_restorer = vDSO の __kernel_rt_sigreturn）へジャンプ
         └─ rt_sigreturn システムコール
              └─ カーネルが uc_mcontext から元の regs を復元
                   └─ IRET → 例外発生前のコードへ戻る
```

| タイミング | 復帰先 |
|-----------|--------|
| IRET 直後 | `ksig->ka.sa.sa_handler`（ユーザーのシグナルハンドラ） |
| ハンドラ `return` 後 | `sa_restorer`（vDSO の `__kernel_rt_sigreturn`）→ 元のコードへ |

## sa_handler の仕組み

`sa_handler` はシグナル番号ごとに独立して登録される関数ポインタ。

```
sighand_struct（プロセスごとに1つ）
    action[0]  → k_sigaction { sa_handler = ... }   // SIGHUP(1)
    action[1]  → k_sigaction { sa_handler = ... }   // SIGINT(2)
    ...
    action[10] → k_sigaction { sa_handler = ... }   // SIGSEGV(11)
    ...
    action[63] → k_sigaction { sa_handler = ... }   // SIGRTMAX(64)
                                              ↑
                                    _NSIG = 64 エントリ
```

カーネルは配送時に `sighand->action[N-1].sa.sa_handler` を `regs->ip` に書き込んで IRET で飛ばす。ハンドラには `sig`（シグナル番号）が引数として渡され、1つの関数を複数シグナルに登録することも可能。

詳細情報が必要な場合は `SA_SIGINFO` フラグと `sa_sigaction`（`void (*)(int, siginfo_t *, void *)`）を使う。

## kdmpシステムとの関係

### ライブリングバッファへの記録

| 経路 | kdmp_capture_event の呼び出し | 記録されるイベント |
|------|-------------------------------|-------------------|
| do_error_trap (経路A) | traps.c:264 | KDMP_EVENT_EXCEPTION |
| #PF (経路C) | fault.c:1466 | KDMP_EVENT_PAGE_FAULT |
| #GP / #BR / #AC / #MF / #XF / #DB / #BP 他 | なし | 記録されない |

ライブリングバッファ (`kdmp_live_ring_t` in `rsv1`) への書き込みは `kdmp_live_capture()` が行い、`/proc/kdmp_live_ptregs` で参照できる。

`kdmp_capture_event` は `noinstr` 関数内から呼べる場所（`instrumentation_begin()` 以降）であれば挿入可能。経路Bの各例外に共通して拾える1箇所は存在しないため、全パターンを網羅するには各ハンドラへの個別追加が必要になる。

### NMIへの適用可否

`kdmp_capture_event` → `kdmp_live_capture` をNMIから呼ぶ場合、`instrumentation_begin()` 以降（`default_do_nmi` 内）に配置すれば呼び出し自体は可能。ただし現在のリングバッファは IRQ と NMI の同時書き込みに対して安全ではない。

```
// 競合シナリオ
IRQ: seq = READ_ONCE(write_seq) → seq=5
     WRITE_ONCE(events[5].committed, 0)
     [フィールド書き込み中 ← ここでNMI割り込み]

NMI: seq = READ_ONCE(write_seq) → まだ5（同一スロット）
     events[5] に NMI データ書き込み
     WRITE_ONCE(write_seq, 6)

IRQ: [再開] events[5] の残りフィールドを上書き → NMIデータ破損
```

修正には `write_seq` を `atomic64_fetch_add` によるアトミック取得に変更する必要がある。

### カスタムダンプ (`status[PANIC]`) への保存

ユーザーモードCPU例外でアプリが終了するすべての経路において:

- `die()` は呼ばれない → `kdmp_ecxt_regs[cpu]` はセットされない
- `panic_dump_gprs()` / `kdmp_panicdump_exec()` は走らない
- カスタムダンプ領域 (`status[PANIC]` 等) への保存は発生しない
- kdump も発動しない、システムは継続する

## pt_regs保存のフック設計指針

### 「誰がいつ参照するか」による分類

```
CPU例外
    ├─ user_mode == true（ユーザープロセス例外）
    │    ├─ パニックしない → システム継続 → ユーザーランドから参照可能
    │    │    → フック: do_error_trap（A）/ handle_page_fault（C）が現実的
    │    └─ パニックする（PID1等） → 参照不可（kdump後の解析のみ）
    │
    └─ kernel_mode == true（カーネルプロセス例外）
         ├─ fixup で回復 → 継続（通常フックなし）
         ├─ panic_on_oops=0 → プロセス終了 → 継続 → 参照可能（現状フックなし）
         └─ panic_on_oops=1 / in_interrupt → panic → 参照不可（kdump後のみ）
```

### フック箇所と目的の対応

| 目的 | 推奨フック箇所 | 理由 |
|------|--------------|------|
| ライブ参照（ユーザーランド） | `do_error_trap`（A）/ `handle_page_fault`（C） | システム継続中に `/proc` で読める |
| クラッシュ解析（kdump後） | `__die_body` → `kdmp_ecxt_regs` | vmcore に残る |
| panic直前の最終状態 | `vpanic` 先頭の `panic_dump_gprs()` | 確実に走る唯一の箇所 |

`panic_on_oops` を設定した瞬間に「ライブ参照」は設計として成立しなくなる。その場合はフックの目的を「kdump後の解析向け保存」に切り替え、`__die_body` → `kdmp_ecxt_regs` → vmcore という経路で回収する。

## 特定ユーザーアプリのpanic条件設計（要求⑦）

現状のカーネルは「ユーザーモード例外 → シグナル → プロセス終了」で常にpanicしない。特定アプリ・特定例外でpanicさせるには判定ロジックの追加実装が必要。

### 明確にすべき条件の軸

```
パニック条件 = アプリ識別 × 例外種別 × サブ条件
```

**軸1: アプリの識別方法**

| 方法 | 実装 | 注意点 |
|------|------|--------|
| プロセス名 | `current->comm` | exec で変更可能 |
| TGID / PID | `current->tgid` | 起動のたびに異なる |
| 実行ファイルパス | `current->mm->exe_file` | より確実だがオーバーヘッドあり |

**軸2: 例外の種別**

シグナル番号だけでは粒度が粗い場合がある。

```
SIGFPE  ← #DE（ゼロ除算）も #MF（FPU例外）も同じシグナル
SIGSEGV ← #GP / #PF / #SS 等が混在
→ trapnr（例外ベクタ番号）まで見るか、signal + si_code の組み合わせで絞るかを決める
```

**軸3: サブ条件**

| 例外 | サブ条件の例 |
|------|-------------|
| #PF (SIGSEGV) | フォルトアドレスの範囲（NULLアクセスのみ等） |
| #MF / #XF (SIGFPE) | si_code (FPE_INTDIV / FPE_FLTOVF 等) |

### フック挿入の候補箇所

```
CPU例外
    ↓
do_error_trap / 専用ハンドラ
    ↓
    ★ 候補①: force_sig_fault の直前
       trapnr と regs が両方ある。経路A/Cは拾いやすいが経路Bは個別対応が必要
    ↓
force_sig_fault → シグナルキューへ追加
    ↓
irqentry_exit_to_user_mode
    ↓
    ★ 候補②: arch_do_signal_or_restart の前
       全シグナルを一箇所で拾える。ただし trapnr は current->thread.trap_nr
       経由でのみ取得でき確実性にやや難。例外以外のシグナルも通過する。
    ↓
get_signal → handle_signal
```

### 条件定義の例

```c
struct kdmp_panic_policy {
    char comm[TASK_COMM_LEN]; /* 対象プロセス名 */
    int  signal;              /* SIGSEGV / SIGFPE 等 */
    int  si_code;             /* 0 = 全サブ種別、FPE_INTDIV 等 */
    u32  trapnr;              /* 0 = 問わない、X86_TRAP_DE 等 */
};

/* 例:
 *  comm="my_app", signal=SIGSEGV, trapnr=X86_TRAP_PF → NULLアクセスでpanic
 *  comm="my_app", signal=SIGFPE,  trapnr=X86_TRAP_DE → ゼロ除算でpanic
 *  comm="my_app", signal=SIGFPE,  trapnr=0           → 全FPE例外でpanic
 */
```

条件が未定義のままフック実装を始めると、条件の後付け変更でフック箇所も変わる可能性がある。実装前に①〜⑤を確定させること。

```
① どのアプリか     → comm / tgid / exe_file のどれで識別するか
② どの例外種別か   → シグナル番号のみか、trapnr まで絞るか
③ サブ条件は必要か → si_code / error_code / フォルトアドレス範囲
④ 複数アプリ対応か → テーブルで複数エントリを管理するか
⑤ watchdog停止    → panic 直前に停止処理を挟む箇所（vpanic内）
```

## 補足: ユーザーランドアプリからのpt_regs参照可否まとめ

| ケース | システム状態 | `/proc/kdmp_live_ptregs` 参照 | vmcore |
|--------|------------|-------------------------------|--------|
| #DB / #BP（デバッグ、nopanicケース） | 継続 | **可能** | なし |
| SIGSEGV 等（通常アプリ） | 継続（アプリは死ぬ） | **可能**（別プロセスが読める） | なし |
| カーネルoops（panic_on_oops=0）| 継続 | **可能**（現状フックなし） | なし |
| panic_on_oops=1 / in_interrupt | **停止** | **不可** | **あり** |
| PID1 死亡 → panic | **停止** | **不可** | **あり** |
